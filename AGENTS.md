# Project Overview

Porter is a private Docker registry platform. It wraps CNCF Distribution (`registry:3.1.0`) with a Go API server and React console for authentication, project management, and image tagging.

**Stack:**

- **Registry:** CNCF Distribution v3.1.0 (token auth, R2/FS storage)
- **API:** Go 1.23, chi router, pgx (Postgres), go-redis
- **Console:** React 18, Vite, TanStack Query, React Router, Tailwind CSS
- **Infra:** Postgres 16, Redis 7, Docker Compose

## Common Commands

### Development Environment

```bash
# Generate auth certs (required before first run)
bash scripts/generate-auth-cert.sh

# Start dev stack (registry on :5000, API on :3000, console on :4173)
docker compose -f docker-compose.dev.yml up -d --build

# View logs
docker compose -f docker-compose.dev.yml logs -f api

# Stop
docker compose -f docker-compose.dev.yml down
```

### API (Go)

```bash
cd api

# Build
CGO_ENABLED=0 go build -o /tmp/registry-api ./cmd/server

# Run locally (requires Postgres + Redis + .env)
go run ./cmd/server

# There are currently no Go tests in the repo.
```

### Console (React)

```bash
cd console

# Dev server
npm run dev

# Build
npm run build

# No test suite configured.
```

### Database Migrations

Migrations are in `api/internal/db/migrations/*.sql` and managed by `pressly/goose/v3`. They run automatically on API server startup via `db.Migrate()`. To add a migration, create a new `.sql` file and follow goose naming conventions.

## High-Level Architecture

### Auth Flow (Docker Registry Token Auth)

The Docker CLI authenticates against the registry using a Bearer token flow implemented entirely by the Go API server:

1. `docker login` hits the registry (`/v2/`), which returns `401` + `WWW-Authenticate` challenge pointing to the API's token endpoint.
2. The CLI sends Basic Auth credentials to `GET /api/registry/token`.
3. The API validates the user (or robot token) against Postgres, resolves permissions from the `members` table, and issues an RS256 JWT signed with `registry/certs/auth.key`.
4. The registry validates this JWT using `auth.crt` and `jwks.json` (generated by the API on startup).

There are **two separate auth systems**:

- **Registry tokens:** RS256 JWTs, short-lived (15 min), signed with RSA private key. Used by Docker CLI.
- **Console sessions:** HMAC-SHA256 "JWT-like" tokens, long-lived (7 days), stored in `HttpOnly` cookies. Used by the React console. See `api/internal/session/session.go`.

### API Response Format

All JSON API responses use a standard envelope:

```json
{ "code": 200, "msg": "", "data": ... }
```

- `code` mirrors the HTTP status code.
- `msg` carries a human-readable message on errors.
- `data` contains the payload on success.

Handlers write responses via `httpx.JSON` in `api/internal/httpx/errors.go`. The Docker registry token endpoint (`GET /api/registry/token`) is the one exception: it uses `httpx.RawJSON` to preserve the exact token format the Docker CLI expects. The React console fetch wrapper in `console/src/lib/api.ts` automatically unwraps the `data` field.

### Permission Model

- **Global:** `platform_admin` (full access), `user` (regular user)
- **Project-level:** `owner`, `developer`, `guest`
- Project permissions are checked via `api/internal/authz/authz.go` (`RequireMember`, `RequireRole`).
- The registry token endpoint intersects requested scope actions with the user's actual grants (e.g., a `guest` only gets `pull`).

### Webhook Event Processing

The registry pushes push/delete events to `POST /internal/registry/events` (authenticated with `WEBHOOK_SECRET`). The API:

1. Deduplicates via Redis (`MarkWebhookEvent`, 24h TTL).
2. Ensures the project/repository exists in Postgres.
3. Upserts manifests and tags on push, or soft-deletes tags on delete.
4. Logs audit events asynchronously.

### Async Audit Logging

`api/internal/audit/service.go` uses a buffered channel (capacity 1000) with a background worker goroutine. If the queue is full, events are dropped (logged as warnings). This prevents audit I/O from blocking request handlers.

### Registry Config Templating

The production registry image wraps the official `registry:3.1.0` with a custom entrypoint (`registry/entrypoint.sh`). At startup it runs `envsubst` on `/etc/distribution/config.yml.template` to produce the final config. This allows environment variables (like `${REDIS_PASSWORD}`) to be injected into the registry config file.

## Code Organization

### Go API (`api/`)

Each domain follows a `repo → service → handler` layering:

- **Repo:** Direct database access (pgx/sqlc-style, no ORM).
- **Service:** Business logic, validation, cross-domain orchestration.
- **Handler:** HTTP request/response handling with chi.

Shared packages:

- `api/internal/httpx` — JSON helpers, custom errors (`BadRequest`, `Unauthorized`, etc.), middleware (CORS, request ID, logging, recoverer).
- `api/internal/authz` — Shared project-level permission checks.
- `api/internal/password` — Bcrypt hashing.
- `api/internal/redisx` — Redis client wrapper with rate limiting and webhook dedup.

### Console (`console/`)

- `src/lib/api.ts` — Centralized fetch wrapper with `APIError` handling. All API calls use `credentials: 'include'` for cookie-based sessions.
- `src/lib/query.ts` — TanStack Query client setup.
- `src/router.tsx` — Route definitions with `RequireAdmin` guard for `/users` and `/audit-logs`.

## Important Conventions

- **Module path:** `github.com/zzzgydi/porter/api`
- **No Go tests exist** in the repository yet.
- **No linting config** (golangci-lint, eslint) is currently set up.
- Environment variables are documented in `.env.example`. The API reads them via `api/internal/config/config.go`.
- In dev mode (`DEV_MODE=true`), the API returns CORS headers for `http://localhost:4173` and uses lax cookie settings.
- The `registry/certs/` directory contains `auth.key` (RSA private key for signing registry tokens) and `auth.crt` (public cert). The API auto-generates `jwks.json` from `auth.crt` on startup if it doesn't exist.
